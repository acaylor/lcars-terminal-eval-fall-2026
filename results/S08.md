## Source inspection notes (file:line)

### Architecture & main loop
- Entry: main.rs:1-3 → `app::main_entry` (app.rs:394-417). CLI parse is app.rs:425-529. `run` (app.rs:270-291) installs the panic hook and signals, checks TERM=dumb, builds the collector, then calls `Terminal::enter` and `run_loop`.
- `run_loop` (app.rs:212-267): check signal flag, `poll_event(100ms)`, dispatch key, `sample_if_due`, advance clock/phase, `draw`. Sampling is scheduled by `next_sample` (1 s, `SAMPLE_INTERVAL` model.rs:6). Animation runs at about 10 fps.
- Rendering is pure: `render_frame(&UiState, w, h) -> Buffer` (views.rs:35-52). Output goes through `Presenter::present` (buffer.rs:206-269). The layout is plain rect math (layout.rs:76-258).
- Weakness: views.rs (2015 lines) has many near-duplicate meter/text blocks (e.g., the CPU bar loop at views.rs:509-530 and 903-924).

### OS collector interface & macOS backend
- `Collector { sample(elapsed, want_processes), initial_metrics, backend, reset_baseline }` (collect.rs:9-14). Its only implementation is `SysinfoCollector` (collect.rs:22-222).
- There is no hand-written Darwin code. On macOS, sysinfo 0.39 provides host_statistics64/host_processor_info (CPU, per-core, memory), sysctl (load, swap, boot time), libproc (process list, per-process CPU and memory) and getifaddrs/if_data (network). clippy on the darwin target is clean (clippy-darwin-deny.log). Natively built and tested 38/38 on macOS.
- **macOS bug in the app's own FFI:** `let block = stat.f_frsize.max(stat.f_bsize) as u64;` (collect.rs:259). On Darwin, `statvfs.f_bsize` is the preferred I/O size (1 MiB) and `f_frsize` is 4 KiB, so totals are 256x too large. macOS capture: `70.7T / 115T` vs `df` 482,797,652 KiB (~460 GiB). The percentage (61 %) is a ratio and survives the bug, but it is container-wide (total−avail), not df's 7 %.
- OS label is `System::name()` = "Darwin 27.2" with arch aarch64. That is acceptable.
- Memory on macOS follows sysinfo semantics (used 4.25G of 24G), which is lower than Activity Monitor would show. This is not the app's bug.

### Forbidden-subprocess check
- No `Command::new`, `popen` or `system(` anywhere (static-scan SUBPROCESS 0, confirmed by reading every file). Time comes from libc `localtime_r` (clock.rs:21-40). Disk comes from `statvfs` (collect.rs:251-266).

### Rate math & robustness edge cases
- Measured dt: `now.saturating_duration_since(self.last_sample)` (app.rs:131) is passed to `RateTracker::update` (collect.rs:172 → model.rs:116-148).
- Counters are tracked per interface in a BTreeMap. If either counter moves backwards, that interface contributes nothing for the interval (model.rs:130). A new interface is only baselined. A vanished interface is dropped (`self.prev = next`, model.rs:138). Intervals under 0.05 s or over 30 s return `None`, shown as "SYNC" (model.rs:140).
- Pause/resume re-primes baselines (app.rs:151-163, collect.rs:216-221).
- Snapshot mode and the capture binary pass a fixed `Duration::from_millis(wait_ms)` instead of measured time (app.rs:303, capture.rs:29). This is minor and not on the interactive path.
- PID churn: sysinfo `remove_dead_processes=true` (collect.rs:163). **Linux processes include threads**: `system.processes().len()` (collect.rs:167) and `collect_processes` (collect.rs:224-236) never filter `thread_kind()`. Count is 1626 vs 506 and the top-5 contains thread entries.
- Names: `sanitize_ui_text` (model.rs:165-197) clips by display width and replaces controls with `?` and wide characters with `·` (lossy but grid-safe). Long hostnames are clipped to 28 (views.rs:256). Process names are clipped to 21 (views.rs:1490). Buffer-level width guard: buffer.rs:111-117. The kernel string is not clipped (views.rs:1222); the buffer bounds stop overflow off-screen.
- Fault degradation: every metric is an `Option` rendered as N/A, SYNC, NO SWAP or a dashed rail. Load is validated as finite and non-negative (collect.rs:101-116). Memory total 0 gives `None` (collect.rs:92-96). statvfs failure gives `None` (collect.rs:256-257). A panic in `sample` is caught and the last sample is kept with SENSOR FAULT (app.rs:133-146), with panic output silenced via `QUIET_PANIC` (term.rs:87-89).

### unsafe / FFI / panic audit & bounded memory
- clock.rs:24/26: zeroed `libc::tm` and `localtime_r` with a null-check. Sound.
- collect.rs:254-255: `CString::new("/")` plus zeroed `statvfs` with an rc check. Memory-sound, but the block-size field choice is wrong on macOS (above). `checked_mul` guards overflow (collect.rs:260-261).
- term.rs:96-109: `libc::signal` for SIGINT/TERM/HUP. The handler only stores to an `AtomicI32` (term.rs:112-114), which is async-signal-safe. The main loop polls it every 100 ms or less (app.rs:217-219).
- No unsafe site has a SAFETY comment.
- Cargo.toml:28-32 has no `panic = "abort"`, so unwind is the default. The panic hook restores the terminal first (term.rs:84-93), and `Terminal` has an RAII `Drop` (term.rs:62-66). `emergency_restore` is idempotent through the `ACTIVE` swap (term.rs:68-82). It hard-codes the title "Terminal" on exit instead of restoring the original (cosmetic).
- Bounded memory: `push_capped(…,120)` (app.rs:387-392). Top-5 is truncated (model.rs:160). The presenter keeps one previous frame. Probe RSS is flat at 4252 KiB over 60 s.
