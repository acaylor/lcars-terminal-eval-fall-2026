Conflict of interest

The evaluator and all nine blind grading agents ran on Claude Opus 5.5, which is also the winning contestant. Claude Fable 5.1, in second place, comes from the same lab.

A model might still recognise its own style, so weigh the judgement-based items with that in mind.

macOS audit

03

Eight of nine READMEs said plainly that the author never ran the macOS build; Gemini's says nothing either way. We built each one natively on an Apple M4 (macOS 27.2) and compared its screen against sysctl, vm_stat, top and df taken at the same moment.

ModelApproachWhat broke on real hardwareScore /5

The Mach-tick trap

On Intel Macs, proc_taskinfo.pti_total_user and pti_total_system are nanoseconds. On Apple Silicon they are Mach absolute-time ticks from a 24 MHz timebase, so they have to be scaled. Skip the scaling and process CPU reads about 40 times too low.

ns = ticks × timebase.numer / timebase.denom = ticks × 125 / 3 # M4: one tick ≈ 41.7 ns

Got it wrong: Fable 5.1, GPT-6.1 Sol, GPT-6 Astra, Grok 4.7. Scaled correctly: Opus 5.5, Gemini 4.

The PID-count trap

proc_listallpids(NULL, 0) returns how many PIDs exist, not how many bytes to allocate. Treat the count as a byte size and the buffer ends up too small, so the process list is silently cut short and the top-5 misses busy processes.

n = proc_listallpids(NULL, 0) # a count buf = calloc(n + slack, sizeof(pid_t)) # not n bytes

Got it wrong: Gemini 4 (297 of 915 processes), Grok 4.7 (74 of 916).

Neither bug shows up in a cross-compile, go vet, clippy, or a code review that trusts the man page. Both appear only when the binary runs on Apple Silicon.

Performance

Linux, Ryzen 9 7900X, 120×36 PTY. Startup is the median of 15 launches; steady state is an 8-second window after 2 seconds of warm-up. Lower is better in every column, and each bar is scaled to its own column.

All nine are far inside the 250 ms startup target, none sent a full-screen clear during steady-state refresh, and memory stayed flat or bounded over a further 60 seconds. CPU resolution is 0.125% (100 Hz ticks over 8 s), so 0.0% means less than one tick. Grok rewrites every changed row in full, sending close to a full screen each second. Muse is the only entry above 1% idle CPU. Kimi and DeepSeek pay for sysinfo's initial scan at startup.

Lifecycle

06

Each monitor was stopped five ways inside a 120×36 PTY, with the terminal's termios state recorded before launch and after exit. A pass means it exited, restored termios exactly, left the alternate screen and showed the cursor again. The same run was repeated natively on macOS.

  • Every monitor survived 80×24, 40×10 and 20×5, and a live resize from 120×36 to 80×24 to 30×8 and back, without a panic.
  • Gemini and Grok build with panic = "abort" but install a panic hook that restores the terminal first.
  • The one latent risk: GPT-6 Astra's sampler goroutine has no recover, so a collector panic would skip restoration.
  • Kimi and DeepSeek send no colour reset after the quit key, but their last frame already ends in one. DeepSeek also renames the window title to "Terminal" on exit.
  • All nine detect redirected output and exit with a message that says what to do.

07

Three deductions in total. Two are for the same thing: an in-process microbenchmark presented as whole-program startup time.

The main view never shows memory available, which the brief requires. Per-core CPU is cut off at 120×36 and the frame breaks at 40×10.

Timed from the top of main. The README admits further down that the figure excludes exec, which contradicts the headline. That partial disclosure is why the deduction is half of Gemini's.

Patterns

08

Looks and engineering mostly disagree

Gemini tied Opus for the best-looking screen (9.5) yet scored 63 of 70, the only entry to fail cargo fmt --check. GPT-6.1 Sol scored a modest 8.0 visually but 67.5 on engineering, from the smallest codebase in the field. The two axes agree only at the ends: Opus led both, Muse trailed both.

sysinfo is not free

The two entries that used the crate started 40 to 90 ms slower than the rest, and on Linux both listed threads as processes: about 1,630 against roughly 505 real ones, with duplicate thread IDs in the top-5.

No TUI frameworks, nine renderers

Every entry hand-rolled a cell buffer and a diff renderer. Eight diff at the cell or span level; Grok diffs whole rows. Toolchain hygiene was nearly universal: eight of nine were fmt- and lint-clean on Linux and on the darwin target.

Method

09
  1. SnapshotCopied each original into S01–S09 with a seeded shuffle, stripping git history, binaries, cost files and the submitted screenshots. The originals were never touched.
  2. ProbeScripted release builds, tests, fmt and lint; PTY sessions with five exit paths, four sizes, live resize and seven colour modes; startup and steady-state performance.
  3. Run on a MacNative build, tests and the same PTY probes on an M4, compared against live sysctl, vm_stat, top and df.
  4. Grade blindOne isolated agent per snapshot, with access only to the brief, the rubric, its own snapshot and its own probe output.
  5. Calibrate blindCompared all nine scorecards item by item, fixed two arithmetic errors and put macOS scores on one severity ladder.
  6. Lock, then unblindMade every scorecard read-only, then opened the model mapping and added the human visual scores.

Hosts

Caveats

  • The Mac's toolchain had no clippy, so macOS code paths were linted from Linux against aarch64-apple-darwin.
  • The capture renderer drops bright-magenta backgrounds in the 16-colour images. Graders checked the raw streams; no score depends on the images.
  • The screens in the dossiers are the evaluator's fresh captures on the Linux host. Before publication, hostnames, process names and network identifiers in every capture and log were replaced with stand-ins such as linux, mac-host and svc07.
  • One host per OS. Absolute timings will differ on other hardware; the ratios should hold.
